# 花生片 Penaup 产品重构设计

## 1. 定位与命名

花生片 Penaup 是一台把手机里的瞬间显影到彩色电子纸上的电子墨水屏拍立得。产品语言不再使用“相框后台”或“胶片工具”作为第一叙事，而是围绕三个动作展开：拍下、显影、留下。

推荐仓库名：`penaup-eink`。如果需要拆分仓库，建议使用 `penaup-firmware`、`penaup-app`、`penaup-web`、`penaup-cloud`。当前仓库保留 `firmware/penaup` 中的 `FRAMEFILM_*` 和历史 BLE 设备名作为兼容层，并在用户界面中统一使用“花生片 Penaup”。

## 2. 视觉与交互方向

视觉主题是“编辑部纸张 × 六色电子纸”。主色为接近白色的灰白草纸和墨黑，强调色只从电子纸的黑、白、红、黄、蓝、绿中取值。标题使用系统宋体/衬线字体，正文使用系统无衬线字体，规格和协议使用等宽字体。页面以细线、章节编号、留白、纸张卡片和轻微噪点层建立质感，不使用大面积通用渐变和高饱和营销卡片。

用户流程被设计成一条短故事：打开工具先看到“今天想留下哪一刻”，连接设备后显示设备和纸面规格；选择照片时，照片进入纸张预览；处理阶段显示“正在显影”，传输阶段显示“正在写入电子纸”；成功后给出一张可再次发送的最近照片卡。所有动画都必须是状态的表达而不是装饰，并且在减少动态偏好或低性能设备上降级为淡入和进度变化。

## 3. 运行时架构

第一阶段采用 Node.js 24 单体运行时：Fastify 负责 HTTP API 与静态托管，SQLite 负责设备、媒体、命令和事件，MQTT 作为可选的 Wi-Fi 设备事件桥，SSE 负责管理页的实时状态。BLE 仍由 Web Bluetooth 和微信小程序直接连接设备；照片在端侧生成 `.film`，服务端只保存已转换文件并为 Wi-Fi 设备提供拉取地址。这样不引入 Redis、Postgres、任务队列或微服务。

```text
Web / 小程序 -- BLE --------------------> Penaup 设备
    |                                      |
    +-- HTTP 上传/管理 --> Fastify + SQLite + 文件存储
    |                                      |
    +-- SSE 状态流 <----- MQTT bridge <---- Wi-Fi 设备
```

MQTT 不承担用户数据的唯一存储，也不替代设备心跳 HTTP 接口。没有配置 broker 时，运行时仍可完整提供 BLE、本地上传、设备心跳和轮询管理能力；配置 `PENAUP_MQTT_URL` 后才启用事件桥接。

## 4. 迁移策略

现有 FastAPI 服务保留在仓库中作为历史实现和协议参考，不再作为新部署入口。Node 运行时先覆盖健康检查、设备心跳、设备列表、媒体存储、设备命令和事件流；模板渲染等高阶能力继续由端侧/历史服务提供，待 Node API 的验收通过后再按模块迁移。这样可以先改变运行时边界，不牺牲现有三机型固件的可回滚性。

## 5. 验收标准

- 用户看见的产品名、仓库文档、网页、微信小程序统一为“花生片 Penaup”。
- BLE 命令值、film 头格式、六色编码和三机型构建约束保持不变。
- Web 工具具备连接、上传、显影、传输、失败重试和减少动态降级状态。
- 微信小程序首页、创作页、传输弹窗和底部导航使用同一套纸张/六色设计语言。
- Node 运行时在无 MQTT 配置时可以启动并通过健康检查、心跳和设备列表测试；有 MQTT 配置时只增加事件桥接能力。
- 新增和改造代码版权标注为 `poboll`；历史第三方/外包来源不在未核验时被错误宣称为独占原创。
